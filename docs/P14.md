# P14 — Multi-Week Drift Detection, Workload/Performance Feedback & Automatic Plan Correction

## Objective

P14 makes StudyOS respond to a course that is gradually going off track without turning the system into a self-escalating workload machine.

P8 already measures current retention/risk. P13 calibrates the first real evidence. P14 adds a different question:

> Across completed teaching weeks, is this course moving in the wrong direction, and if so, should today’s fixed study capacity be reallocated?

The phase intentionally changes **allocation**, not total workload.

## Evidence windows

Current-week incompleteness is excluded from drift scoring.

For each major course StudyOS looks at:

- the two most recently completed teaching weeks;
- up to two completed weeks immediately before them;
- independent attempt accuracy;
- actual question-solving minutes;
- actionable weekly-workflow lag;
- unresolved reconciliation errors.

A course needs at least two completed weeks plus either a real independent-attempt sample or two weekly-workflow rows before P14 is allowed to classify drift.

Until then the state is `insufficient_data`.

## Drift signals

P14 scores only sustained or repeated signals:

- one or more completed weeks still stuck on an actionable workflow step;
- recent independent accuracy below a conservative floor;
- a material accuracy decline against the prior completed-week window;
- repeated unresolved errors;
- **underinvestment** — effort falls while workflow/performance weakens;
- **low-yield effort** — time rises materially without a matching performance gain.

Improving accuracy without materially more time is classified as effective workload rather than as a reason to add work.

The resulting bands are:

- `insufficient_data`
- `on_track`
- `watch`
- `drifting`
- `critical`

The score is explanatory, not a mastery score.

## Workload/performance feedback

Each course receives one workload/result interpretation:

- **insufficient data**
- **stable**
- **underinvested**
- **low yield**
- **effective**

This distinction matters. A student who is spending too little time needs a different correction from a student who is spending more time but still getting worse results.

## Automatic plan correction

P14 feeds directly into the existing P10 planner.

It never changes:

- the selected capacity mode;
- the configured daily minute budget;
- the review ceiling;
- deadline urgency;
- exam-strategy authority.

Instead it may:

1. add a small priority boost to ordinary course workflow/checkpoint tasks;
2. inject one bounded targeted-practice candidate when the evidence says the problem is performance/efficiency rather than simply unfinished workflow;
3. let P10’s existing course-balancing penalty prevent one drifting subject from monopolizing the day.

The correction sizes are deliberately bounded:

- watch → mild rebalancing;
- drifting → stronger rebalancing, usually up to a 20-minute replacement block;
- critical → strongest rebalancing, usually up to a 30-minute replacement block.

These minutes are **inside** the existing daily capacity. They replace lower-value work rather than extending the day.

Recovery Mode still suppresses optional P14 repair unless another existing rule makes work urgent.

Exam/transition-mode courses do not receive an injected P14 practice block because P9 exam strategy remains the higher-level controller there.

## UI

### Today

When a course reaches watch/drifting/critical:

- the strongest current drift signal appears below the daily plan;
- StudyOS explains the workload/result interpretation;
- recent vs prior practice time and accuracy movement are shown;
- the exact allocation-priority boost is visible;
- the unchanged total daily budget is stated explicitly.

### Progress

Each course shows:

- drift band and score;
- recent accuracy;
- change versus the prior completed-week window;
- recent/prior practice minutes;
- lagged teaching weeks;
- unresolved errors;
- workload/result interpretation;
- the strongest contributing drift components;
- the recommended correction.

## Architecture

P14 does not add another database state machine.

The drift profile is derived from existing source-of-truth data:

- `study_attempts`
- `study_week_actions`
- `study_questions`
- current semester/course configuration

No new mastery evidence is created by the drift model itself.

## Safety / anti-overreaction rules

P14 must never:

- score an unfinished current week as failure;
- infer drift from one isolated bad attempt;
- increase total study capacity automatically;
- override deadlines;
- override exam strategy;
- manufacture practice when no verified questions exist;
- turn early-semester missing data into a negative signal.

## Next phase

P15 should focus on **semester-level learning analytics and intervention validation**: verify whether P14 corrections actually improve subsequent weeks, detect repeated failed interventions, and distinguish temporary noise from structural course difficulty.
