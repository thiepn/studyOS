## Demonstrated source defects and fixes

- `getFirstWeekProof` silently discarded all independent attempts after the first 1,000, potentially falsely marking a real major course's Week-1 attempt missing or undercounting attempts. Bounded, owner-scoped, unique-ID ordered pages of 500 (batched 40 question IDs) replace the fixed limit. If 20,000 records are reached, the handler fails closed and reports an incomplete proof instead of treating partial proof as complete. This is a **source/synthetic test** qualification, not a real Supabase benchmark.
- Existing recovery custody `inspectOfflineCustody` treated all JSON arrays up to 10,000 records as retryable, although writes cap attempts at 100 and session starts/finishes at 20. The inspector now enforces those exact queue capacities, bounds very large raw JSON before parsing, accounts for legacy-unowned entries, and exposes source-byte pressure/full queues without revealing answer bodies.
- `StudySyncBridge` previously relied on list helpers that returned an empty array for malformed localStorage, masking original work as `0 pending`. It now uses the same strict owner-verified custody scanner as explicit Account Recovery, blocks automatic replay for malformed/legacy/owner-mismatched queues, shows a keyboard-accessible recovery link with polite status, and prevents overlapping same-tab sync calls.
- The dedicated Account Recovery view shows occupied capacity and approximate UTF-16 local storage volume, retaining the original warning not to clear browser storage.

## Outstanding limits / external release blockers

Real Supabase owner RLS/read-back permissions and deployed migrations, large-data performance/load profiling against permissioned disposable accounts, actual university-approved Week-1 source/question/attempt, Google Drive/Calendar OAuth consent, physical Android/Samsung Internet/installed PWA and iPad/assistive technology, encrypted off-device original restore and source-rights/signer/human approvals all remain unverified. Existing localStorage writes outside participating Web Locks can still race across tabs; no claim of atomic cross-tab evidence preservation or cross-device queue transfer. Full queue handling still rejects new writes instead of overwriting original bytes. Service receipts and application claims are not a substitute for independent read-back or acceptance.
