# P8 — Longitudinal Retention Diagnostics, Cumulative Checkpoints, Course Risk Detection & Exam-Transition Engine

## Purpose

P8 changes StudyOS from a state tracker into a semester-control system. It should answer four questions continuously:

1. What knowledge is beginning to decay?
2. Which course is becoming dangerous?
3. Which course gets this week’s cumulative checkpoint?
4. Has a course entered exam preparation mode?

## Retention diagnostics

Each skill is classified as one of:

- `untested`
- `maintained`
- `due`
- `overdue`
- `lapsed`
- `relearning`

The diagnostic retains the five evidence dimensions individually and calculates a retention-pressure score from evidence deficit, overdue time, lapse count, and relearning state. Untested material is deliberately separated from forgotten material.

Course-level diagnostics aggregate:

- tested vs untested skills
- due / at-risk skills
- 7+ day overdue skills
- relearning skills
- recent lapse skills
- 28-day attempt outcomes
- average retention pressure

## Rotating cumulative checkpoint

P5’s per-course weekly checkpoint requirement was intentionally removed from the week-action engine.

The semester now has exactly one scheduled major-course checkpoint per week:

```text
Week 1  DGL
Week 2  Stochastik
Week 3  Theoretische Informatik
Week 4  AMP
Week 5  DGL
...
```

The target budget is 60 minutes by default and is separate from the 40-minute ordinary review cap.

Selection is deterministic. It first reserves roughly 60% of checkpoint capacity for material at least two weeks old, then fills remaining capacity by risk/importance. A weak or lapsed skill may outrank an older healthy skill.

Checkpoint priority includes:

- retention pressure
- exam importance
- prerequisite importance
- age
- recent lapse
- current retention state

A checkpoint is recorded as a real `study_sessions.session_type = checkpoint` session. Finishing that session clears the current weekly checkpoint obligation.

## Course-risk engine

Risk is an explainable heuristic, not an AI judgment.

The 0–100 score is composed from:

- retention pressure: up to 25
- reviews overdue 7+ days: up to 20
- recent lapse share: up to 15
- actionable weekly/resource backlog: up to 20
- unresolved errors: up to 10
- exam-readiness gap: added only in transition/exam mode

Bands:

- 0–19 healthy
- 20–39 watch
- 40–59 at risk
- 60–100 critical

The UI exposes the component values and top drivers.

## Exam-transition engine

Per-course defaults:

- transition begins 35 days before the configured exam
- exam mode begins 21 days before the configured exam

Operating mixes:

### Semester

- 60% current coursework
- 35% retention
- 5% exam practice

### Transition

- 35% current coursework
- 30% retention / weakness repair
- 35% exam practice

### Exam mode

- 65% exam practice
- 25% weakness repair
- 10% pure recall

The daily retention queue itself remains capped; exam practice is not disguised as an ever-growing review backlog.

## UI

Today now shows:

- fixed daily review
- this week’s rotating cumulative checkpoint
- highest-risk course and its main drivers
- courses currently transitioning toward exams

Progress now shows each course’s risk band, retention counts, exam-readiness percentage, risk drivers, operating mode, and recommended study mix.

Practice supports a dedicated cumulative-checkpoint session.

## Verification

A rollback integration test demonstrated:

- week 3 rotates to Theoretische Informatik
- the checkpoint is due before completion
- completing a checkpoint session clears it
- a DGL exam 20 days away activates exam mode
- exam mode returns the 65/25/10 mix
- an overdue relearning skill contributes visible retention and overdue risk
- no course week independently emits `weekly_checkpoint`

P8-specific Supabase security/performance advisors returned no findings.
