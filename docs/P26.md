# P26 — Semester Archive, New-Semester Rollover & Retake Carry-Forward

## Objective

P25 tells StudyOS when a semester is academically complete or which retakes remain open.

P26 turns that state into a safe lifecycle transition:

> archive the old semester, preserve it as historical evidence, create one new active semester, and carry only explicit academic obligations that genuinely belong in the future.

## Active-semester authority

Before P26, `ensureStudyWorkspace()` was hard-coded to `ws26_27`.

P26 replaces that assumption with:

```text
study_semesters.active = true
```

All normal StudyOS workflows therefore follow the currently active semester.

A partial unique index guarantees at most one active semester per user.

If a user has historical semesters but no active semester, StudyOS no longer silently reactivates WS26/27. Lifecycle/recovery UI must be used instead.

## Durable lifecycle metadata

P26 adds to `study_semesters`:

- `archived_at`
- `previous_semester_id`

The active/archive invariant is enforced:

- active semester → `archived_at is null`
- archived semester → `archived_at is not null`

`previous_semester_id` creates an explicit rollover ancestry chain.

There can be only one target semester for a given source semester.

## Rollover transaction

P26 adds:

`study_rollover_semester(...)`

The database transaction:

1. validates ownership and permanent-account authentication;
2. locks the source semester;
3. validates the new semester identity/date range;
4. prevents a second active semester;
5. rejects open real commitments;
6. rejects unresolved/provisional/missing academic outcomes;
7. rejects pending retake decisions;
8. requires planned retakes to have a matching future exam date;
9. archives the source semester;
10. closes any still-active P19 weekly plan;
11. creates the next active semester;
12. copies only explicitly planned retakes;
13. initializes fresh course workflow settings;
14. returns the new semester and carried courses.

The transaction is idempotent for the same successful source → target rollover.

## Why pending retakes do not carry

A pending retake decision is not yet a defined future obligation.

P26 therefore requires it to be resolved before archive.

Only:

`retake_decision = planned`

with a future authoritative exam date may carry.

This keeps the archived P24 result immutable as historical context and avoids creating a new course whose academic future has not actually been decided.

## What carries forward

For each planned retake P26 creates a **new course row** in the new semester.

It carries:

- stable course identity;
- display / short name;
- retake course kind;
- professor metadata;
- credits;
- future exam timestamp;
- exam duration / format;
- reusable workflow settings.

It intentionally does **not** reuse the old course row.

The archived semester therefore keeps its own complete historical course identity.

## What does not carry

P26 does not copy:

- P19 weekly plans or allocations;
- unfilled weekly minutes;
- P10 daily candidates;
- prior scheduled blocks;
- sessions;
- mastery/retention state as new-semester debt;
- interventions;
- checkpoints;
- old Drive semester/course folders;
- intake queues;
- old semester forecast state;
- completed or declined courses.

The new semester starts from fresh operational state.

## Open commitments

An open P10 commitment is a real obligation, not stale study debt.

P26 does not guess whether it should disappear or be copied.

Any open commitment blocks rollover until it is explicitly resolved.

## Calendar cleanup

Future committed StudyOS calendar blocks from the source semester do not block the academic transaction.

After a successful rollover, the app cancels them through the existing P11 Google Calendar cancellation path.

If external Calendar deletion fails:

- the semester rollover stays successful;
- the failed StudyOS block remains visible;
- Semester History exposes a retry cleanup control.

This avoids coupling the authoritative academic archive transaction to an external API.

## Retake attempt lineage

P26 does not copy old `study_exam_results` rows into the new semester.

Instead, P24 now builds retake history from:

1. the explicit `previous_semester_id` ancestry chain; and
2. the same stable course key.

This means:

- historical outcomes remain attached to their original semester/course;
- attempt numbering continues across semesters;
- a new retake attempt is written only to the new course;
- unrelated future re-enrolments with the same key outside the ancestry chain are not merged accidentally.

## Archived P25 ledger finality

Historical P25 ledgers are evaluated at:

`archived_at`

rather than the current wall clock.

This matters for planned retakes.

If a retake exam was in the future when the old semester was archived, the archived ledger remains “retake planned” forever.

It does not mutate into “awaiting result” months later merely because that date eventually passed in the new semester.

## Historical access

New routes:

- `/semesters` — active + archived semester history
- `/semester/rollover` — preflight and rollover control
- `/semester/archive/[semesterId]` — read-only historical P25 ledger

The archived ledger exposes:

- final course/credit outcome state;
- attempt history;
- P17 directional outcome evidence;
- P19/P20 execution retrospective;
- stale calendar cleanup status.

It exposes no course/planning mutation controls.

## Rollover preflight

The UI checks:

- active source semester exists;
- no open commitments;
- no pending retake decisions;
- no provisional/missing results;
- no ongoing courses;
- no inactive course lacking a terminal P24 outcome.

Future calendar blocks are shown as cleanup work, not academic blockers.

## New-semester identity

The user explicitly supplies:

- stable key;
- display name;
- start date;
- optional end date;
- timezone.

P26 does not guess the university's next semester dates.

The old semester's review/checkpoint budget defaults are copied as starting configuration.

## Database and security

P26 introduces no new table.

It adds lifecycle columns and two uniqueness indexes to `study_semesters`, plus the rollover RPC.

The existing owner-only semester/course RLS remains authoritative.

The RPC is security-invoker and explicitly granted only to `authenticated`; `anon` and `public` execution are revoked.

This is also compatible with Supabase's 2026 move toward explicit Data API grants: no new public table is introduced.

## Guardrails

P26 must never:

- reactivate an archived fixed-key semester automatically;
- allow two active semesters;
- archive while real commitments remain open;
- archive while a result is missing/provisional;
- carry a pending retake decision;
- copy weekly study debt;
- copy stale calendar planning as new-semester work;
- duplicate historical exam results into the new semester;
- reset retake attempt numbering;
- mutate an archived ledger as future retake dates pass;
- merge unrelated course histories merely because names match.
