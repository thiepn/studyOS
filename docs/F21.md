# StudyOS F21 — Owner-bound offline replay and device acceptance

## Source work and acceptance semantics

F21 introduces an authenticated **read-only** offline receipt endpoint. The endpoint never accepts an owner from the browser. It verifies the authenticated permanent THIEPN Account, filters by the derived user ID and reads only `study_attempt_requests` or `study_sessions` records through the regular Supabase user session (no service role). It returns only `ok` and `recorded`, never academic answers, tokens or another owner's identity.

For attempts, exact request ID plus question ID and a non-null persisted response are required. For sessions, exact session ID and start fields or end timestamp/note are required. An authenticated API positive write response without matching read-back **does not delete local work**. Replay checks receipts *before* POST to avoid duplicating already committed operations after network timeouts and *after* POST before deleting. Owner changes between stages stop replay; Web Locks serialize participating tabs per owner where supported. Browsers without Web Locks still require server-side idempotent writes and receipts and **do not claim cross-tab mutual exclusion**.

Any read permission error, missing receipt, HTML login page, changed queued record, malformed input, full queue or ambiguous server commit retains original local evidence for owner review. Database policy and permissions for the existing receipt tables must be independently verified in disposable staging. No newly invented migration or right-grant is deployed.
