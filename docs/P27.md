# P27 — New-Semester Course Intake, Curriculum Bootstrap & Historical Prior Transfer

## Objective

P26 creates a clean active semester. P27 makes that workspace academically usable without contaminating it with stale semester state.

The operating principle is:

> historical evidence may tell StudyOS what to verify first; only current-semester evidence may establish current mastery.

## General course intake

P27 removes the WS26/27-only course roster assumption.

A new authenticated RPC:

`study_create_course(...)`

creates a real course in the currently active semester and initializes its reusable workflow expectations.

Supported course kinds remain:

- major
- minor
- retake

The user supplies the stable internal key and real course identity instead of StudyOS inventing the university roster.

Adding a course invalidates any previous P27 bootstrap certification.

## Course contract

Course intake can establish:

- stable key;
- display / short name;
- course kind;
- professor;
- credits;
- exam timestamp;
- exam duration / format;
- ordering;
- expected weekly lecture count;
- exercise / official-solution expectations;
- retrieval/reconciliation timing;
- checkpoint weighting.

The existing course configuration page remains authoritative for later edits.

## Active-semester Drive provisioning

Pre-P27 Drive setup and scanning were tied to `ws26_27`.

P27 removes that fixed semester key.

Drive provisioning now:

1. resolves the active semester;
2. reuses the account-level `Semester OS` root;
3. creates/reuses a folder for the active semester;
4. creates/reuses its `00_INBOX`;
5. creates only missing active-course folders/subfolders;
6. writes the active semester's folder IDs back to that semester;
7. updates the connection's current-semester pointers.

Drive scanning likewise resolves the active semester instead of the old fixed key.

The active semester now owns:

- `drive_semester_folder_id`
- `drive_semester_folder_url`

This prevents a rollover from accidentally reusing the archived semester's mutable connection pointer.

## Historical prior transfer

P27 adds:

`study_course_historical_priors`

A prior links a current active course to a course from an archived semester.

Relations are explicit:

- `direct_retake`
- `prerequisite`
- `related`

Each prior stores an immutable advisory snapshot containing limited archived context such as:

- source course identity;
- official attempt count;
- latest outcome / grade / score;
- stored P17 readiness snapshot;
- archived skill count;
- unresolved reconciliation-finding count.

It does **not** copy:

- mastery rows;
- review schedules;
- sessions;
- attempts as current evidence;
- due-state;
- P19 weekly allocation;
- P20 calibration;
- P16 strategy state.

## Secure prior snapshots

Historical snapshot generation is scoped to `auth.uid()`.

Authenticated users cannot request another user's course snapshot by supplying a foreign user identifier.

The prior table uses owner-only RLS and explicit authenticated grants.

## Automatic direct-retake prior

When P26 creates a retake in the next semester and a same-stable-key source course exists in the immediately previous semester, P27 automatically attaches it as a `direct_retake` prior.

Existing active rollover retakes are backfilled when the migration is applied.

No mastery is restored by this automation.

## How priors are used

P27 surfaces historical priors:

- in the new-semester bootstrap dashboard;
- in the retake baseline diagnostic.

The UI explicitly treats them as **diagnostic prioritization context**.

For example, an archived course with unresolved findings can tell the user what to re-check first, but the new-semester skill still starts without current mastery evidence.

## Fresh curriculum requirement

Historical priors cannot substitute for current curriculum evidence.

Every active course must have:

- at least one verified current resource;
- at least one active current skill;
- at least one active current question.

This forces the new semester's study map to be source-grounded again.

## Retake baseline requirement

Every active retake must complete a fresh P12 baseline diagnostic before P27 certification.

The archived prior may guide what to inspect, but the fresh baseline is what classifies retained/rusty/weak/never-mastered state for the new attempt.

## Bootstrap certification

P27 adds `study_semesters.bootstrap_certified_at` and:

`study_certify_semester_bootstrap()`

Certification requires:

1. at least one active course;
2. workflow settings for every course;
3. Study Drive connected;
4. active-semester Drive folder + inbox provisioned;
5. Drive folder for every active course;
6. verified current curriculum resource for every course;
7. active skill + question map for every course;
8. completed fresh baseline for every retake.

The database validates these conditions independently of the UI.

## Runtime gate

For a new rollover semester whose bootstrap is not certified:

- real P10 commitments remain visible;
- ordinary workflow is blocked;
- retention review is blocked;
- exam-strategy / repair / checkpoint work is blocked;
- P19 weekly-plan commitment is rejected.

Today surfaces a direct link to finish P27 bootstrap.

This prevents P12/P17/P18/P19 from manufacturing a study plan before the new curriculum has been anchored.

The original pre-P26 semester is grandfathered as certified so deploying P27 does not disable an already-operational semester.

## Dynamic P12 activation

P27 removes P12's fixed assumptions of exactly:

- six courses;
- four majors;
- two retakes;
- WS26/27.

Activation now evaluates the actual active-semester roster.

A retake-only or differently sized semester can therefore certify correctly.

P12's first-week certification remains separate from P27:

- P27 certifies the curriculum/bootstrap baseline;
- P12 later certifies real first-week timetable, source, map, and attempt evidence.

## UI

New route:

`/semester/bootstrap`

It provides:

- active-semester bootstrap status;
- course intake;
- Drive provisioning/repair;
- per-course readiness;
- curriculum counts;
- retake baseline status;
- attached historical priors;
- archived prior selection;
- explicit bootstrap certification.

Navigation and the Semester page link into this workflow.

## Database changes

P27 introduces one new table:

`study_course_historical_priors`

and adds semester columns:

- `bootstrap_certified_at`
- `drive_semester_folder_id`
- `drive_semester_folder_url`

It also adds/updates RPCs and the active-semester activation view.

## Guardrails

P27 must never:

- infer the new semester's roster from the archived semester;
- restore prior mastery automatically;
- copy old sessions/review schedules into current evidence;
- allow a historical prior to satisfy the current curriculum requirement;
- certify a retake without a fresh diagnostic;
- provision Drive into a hard-coded semester;
- commit a normal weekly plan before bootstrap certification;
- hide real commitments merely because bootstrap is incomplete;
- merge historical course evidence solely by display name.

## Next phase

**P28 — Cross-Semester Transfer Validation, Prior Calibration & Longitudinal Learning Profile**

P28 should evaluate whether historical priors actually helped once current-semester evidence accumulates: compare prior signals against fresh baseline/early attempts, learn which kinds of prior evidence transfer reliably, surface cross-semester durable strengths/recurring weaknesses, and keep that longitudinal profile advisory rather than making it a second mastery authority.
