# P5 — Course Configuration, Weekly Study Loop, Exercise/Solution Reconciliation & Deployment Qualification

## Goal

P5 turns StudyOS from a review/resource foundation into the semester operating loop.

## Course configuration

Each of the six course identities remains stable internally while its user-facing metadata can be edited:

- real course name and short name
- professor
- ECTS
- exam date/time, duration, and format
- expected lectures per week
- whether exercise sheets and official solutions are expected
- lecture-retrieval target
- solution-reconciliation target
- checkpoint weight

The four placeholder major-course names are intentionally not guessed. They can be replaced from the course screen when known.

## Weekly loop

StudyOS derives one next action for each teaching week:

1. await material
2. process newly ingested material
3. retrieve lecture content from memory
4. attempt the exercise sheet independently
5. await the exercise sheet when not released
6. reconcile against the official solution
7. await the solution when not released
8. repair reconciliation findings
9. run a weekly checkpoint
10. maintain through spaced review

Milestones snapshot how many lecture/exercise/solution resources or skills they covered. If a professor releases additional material later, the milestone becomes stale automatically and the relevant action reopens.

## Exercise-before-solution invariant

When an exercise is expected, solution reconciliation cannot be completed unless an independent exercise attempt has already been recorded for all currently released sheets.

This is a workflow invariant, not a UI convention.

## Reconciliation findings

Solution comparison records discrepancies instead of merely marking the sheet “checked.”

A finding stores:

- week
- optional mapped skill
- error category
- severity
- diagnostic title/detail
- repair status

If a finding is mapped to a skill, StudyOS immediately schedules that skill in the review engine with `due_reason = solution_repair`. No evidence score is increased or decreased by the finding itself.

A finding is resolved only after the user independently repairs it.

## Deployment qualification

The repository now contains a GitHub Actions qualification gate that runs on every push/PR:

1. install pinned top-level dependencies
2. run pure behavior tests
3. run TypeScript typecheck
4. run a Next.js production build

Vercel deployment is intended to use normal Git integration from `thiepn/studyOS`. The connected Vercel app must expose a team/project scope before automated project creation or environment configuration can be performed.

## Remaining production setup

Before public use:

- connect/authorize Vercel for the target team
- add the Supabase public URL/publishable key
- add the server-only Supabase service-role key
- configure the separate StudyOS Google OAuth client
- add the Drive refresh-token encryption key
- set the final APP_ORIGIN
- register the final Google OAuth redirect URI
- run browser verification on the deployed preview
