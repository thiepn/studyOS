# P19 — Weekly Commitment, Scenario-to-Plan Translation & Rolling Reallocation

## Objective

P18 is intentionally exploratory. P19 turns one feasible scenario into an operational commitment for the remainder of the current calendar week.

The phase answers:

> “Given the weekly envelope I chose, how should StudyOS keep the day-to-day planner aligned with it as work gets completed and reality changes?”

P19 does not create more capacity. It turns weekly intent into bounded priority pressure inside P10.

## Durable weekly state

P19 adds two owner-isolated tables:

- `study_week_plans`
- `study_week_allocations`

A weekly plan stores:

- commitment window;
- objective;
- capacity source;
- total committed capacity;
- mandatory reserve;
- retention reserve;
- total course budget;
- revision;
- scenario snapshot;
- original commit time;
- latest rebalance time/reason.

Each course allocation stores:

- original committed minutes;
- current target minutes;
- protection floor at commit;
- P17 readiness / decision-priority snapshot;
- current action title/link/authority.

The **original** course minutes are never overwritten. Rebalancing changes only the current target.

## Commitment window

A new commitment starts **today** and ends on the coming Sunday.

This is deliberate:

- Monday-start assumptions are not retroactively imposed when the user commits on Wednesday;
- completed work before the commitment is not charged against the new plan;
- “days remaining” and missed-day pressure are unambiguous.

The next calendar week receives a new commitment.

## Capacity at commit

P19 recomputes the feasible remainder of the current week server-side.

For the days today → Sunday:

1. use the configured P10 daily default;
2. if P11 Calendar is connected, cap today by the remaining free windows after the current clock;
3. use P11 free time for future days;
4. reserve currently open commitments due during the window;
5. reserve retention using the existing P10 review ratio;
6. allocate the remainder across courses with the selected P18 objective.

The API never trusts a client-supplied capacity above this server-recomputed ceiling.

A mandatory-work deficit cannot be committed. A course-floor deficit can be committed deliberately because P18 makes the sacrifice explicit.

## Progress evidence

P19 does not introduce another activity ledger.

Course-envelope progress is derived from existing StudyOS evidence after the commitment time.

### Recorded session minutes

Completed `study_sessions.actual_minutes` are the primary signal. If actual minutes are absent, planned session minutes are the fallback.

### Workflow credit

Some existing course workflow milestones do not create a study session. P19 therefore assigns conservative fixed credit:

- lecture retrieval: 10 min
- exercise attempt: 60 min
- solution reconciliation: 30 min
- checkpoint: 60 min

To avoid double-counting the same work through both paths, P19 uses:

> **credited course minutes = max(recorded session minutes, workflow-credit minutes)**

for each course.

The UI always labels these as **credited** rather than claiming perfect observation of real study time.

Mandatory commitments and retention remain separate reserves; they do not consume course envelopes.

## Pace

Each course is classified against the committed window:

- **not started**
- **behind**
- **on track**
- **ahead**
- **met**

Pace compares credited minutes with the linear expected progress through the commitment window.

A ±30-minute buffer prevents tiny timing differences from constantly flipping the status.

## P10 translation

An active weekly plan modifies only **discretionary course work**.

It never changes priority for:

- explicit commitments/deadlines;
- P9 exam-strategy actions;
- retention review.

P19 adjustments:

- behind / not started: +10
- on track: +4
- ahead: +1
- envelope met: −8

These are priority modifiers only.

They do **not** increase P10's daily budget.

### Fallback course candidate

If a course still has committed minutes remaining but no normal P10/P14/P16 task exists today, P19 may add one bounded `weekly_envelope` candidate.

The fallback:

- links to the current P17 highest-value course action;
- targets at most 45 minutes;
- is splittable;
- remains subject to P10 Recovery Mode, focus limits, cross-course balancing, and the hard daily capacity ceiling.

## Rolling reallocation

P19 continuously derives a rolling proposal from:

- current remaining-week capacity;
- credited course work;
- current P17 priorities;
- the original/current course envelopes;
- the committed P18 objective.

The proposal can identify:

### Capacity loss

The remaining feasible week is smaller than the unspent commitment.

Examples:

- a missed day;
- newly occupied Calendar time;
- newly added mandatory work.

### Evidence shift

A course's P17 decision priority moved by at least 15 points from the last committed/rebalanced snapshot.

### Pace recovery

The week is materially behind and remaining capacity should be redistributed toward the highest-value unfinished work.

## Explicit application

Reallocation is **proposed automatically but applied explicitly**.

This is intentional.

A weekly commitment should not silently rewrite itself behind the user's back.

When applied:

- current target minutes are updated;
- original minutes remain unchanged;
- revision increments;
- P17 action snapshots refresh;
- the rebalance reason and timestamp are recorded.

The total course budget may shrink when capacity has genuinely been lost.

It cannot expand beyond the original committed course budget merely because extra time later appears. To intentionally add more weekly capacity, commit a new feasible plan rather than letting rolling reallocation manufacture extra work.

## Over-completion

If a course exceeds its target, the real credited amount remains visible.

For reallocation math, completion is capped at that course's current target. This prevents over-completion from inflating the committed weekly budget.

## UI

New route:

`/week`

Without an active commitment it shows:

- feasible today→Sunday capacity;
- mandatory reserve;
- retention reserve;
- course budget;
- balanced preview;
- objective/capacity commitment controls.

With an active commitment it shows:

- total credited / target minutes;
- days remaining;
- revision;
- per-course pace;
- original target;
- current target;
- completed and remaining minutes;
- expected progress by now;
- session vs workflow evidence;
- current P17 action;
- proposed target changes;
- rolling-rebalance reason;
- current remaining capacity.

Today also receives a compact P19 card.

P18 links directly to P19.

## Persistence and security

The P19 tables:

- use RLS;
- allow only permanent authenticated owners;
- verify allocation ownership through both the referenced weekly plan and course;
- have covering foreign-key indexes;
- use existing StudyOS `updated_at` triggers.

Supabase security/performance advisors were run after the live migrations. P19 introduced no new security advisory. The only P19 performance notices remaining immediately after creation were expected unused-index notices on empty new tables.

## Authority hierarchy

P19 preserves all existing control boundaries:

- **P9** remains authoritative for exam-preparation method.
- **P10** owns the hard daily capacity and focus-item scheduler.
- **P11** owns actual calendar placement.
- **P17** supplies current strategic action/value.
- **P18** supplies weekly trade-off logic.
- **P19** keeps a selected weekly envelope operational over time.

## Guardrails

P19 must never:

- expand today's P10 budget;
- demote urgent commitments;
- demote P9 exam-strategy work;
- replace retention reserve with course work;
- trust client capacity above server-recomputed feasibility;
- silently apply a weekly reallocation;
- count the same session and workflow milestone additively;
- overwrite the original weekly allocation baseline;
- inflate a weekly budget because one course was over-completed;
- treat credited minutes as perfectly observed real study time.
