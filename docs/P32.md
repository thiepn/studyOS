# P32 — Course & Semester Workflow Simplification (first implementation)

## Product problem

The P31 navigation has a clear hierarchy, but a learner entering a course still encounters a generic all-course review route; self-assessment also asked for *pre-reveal* confidence **after** showing the answer. A revealed solution could be silently skipped instead of producing a record. This is both a workflow and evidence-quality defect.

## Delivered

1. **Course-context retrieval:** `/practice?course=<id>` draws eligible due skills **for that course before the review budget is applied**. It uses the same due-skill filters, question-selection ranking, and effective daily review cap as ordinary review. It never substitutes another course or creates a separate daily schedule.
2. **Contextual course work:** Course binders expose an explicit Review due skills action. Teaching-week repair links lead to the corresponding course queue. The weekly checkpoint action enters actual checkpoint mode instead of generic review.
3. **Honest pre-reveal self-assessment:** Confidence 1–5 is selected before revealing a solution; typed mode requires a nonblank attempt, while paper mode is first-class. The selection is displayed read-only after reveal. A give-up can reveal the rubric, but explicitly records an incorrect, zero-credit attempt requiring an error classification.
4. **State integrity:** No "skip instead" path after the answer key is shown. Duplicate session starts are blocked while start is in flight. Creating a finding only clears its form after a confirmed save.
5. **Visual continuity:** New affordances use the restrained P30/P31 academic paper/ink language, not KPI cards or a chatbot panel.

## Invariants

- No schema or policy migration.
- No new grading model, readiness score, calibration formula, exam forecast, capacity ceiling, or weekly-plan authority.
- The course query is a **manual view** into the existing due queue, not additional automatically scheduled reviews.
- StudyOS still records a self-grade; a human must compare worked answers with a trustworthy solution. Free-text or paper answers are not auto-graded.
- Review attempts, session events, and offline retries use the existing persistence interfaces.
- Existing default `/practice` behavior and navigation remain available.
- Historic storage keys and study evidence are not changed.

## Verification

- Unit tests: review-state confidence/lock gating; course-scope behavior before fixed-budget selection.
- CI: behavior tests, TypeScript, Next.js build.
- Human QA still required: keyboard, paper/typed transitions, slow/offline sync, responsive touch, exam workflow and real course data.

## Remaining P32 workflow scope

Course/week/semester actions still span distinct screens. A later P32 follow-up should reduce handoffs on setup, week commitment, and exam execution **without creating competing write authorities**. Do not mark semester-wide workflow simplification complete until real-user scenario walkthroughs verify those routes end to end.

**Rubric provenance:** When the queue lacks a rubric, StudyOS requires an explicit acknowledgment that the learner checked a reliable external source before a potentially positive self-grade may be saved. A give-up remains zero-credit and does not require this acknowledgment. No grading is automated.

## P32B — In-course execution, source context and checkpoint integrity

This is the second P32 implementation slice, not a new study engine.

### Course-first work
- Course binder's first action jumps to the featured teaching week. An empty course goes directly to a preselected material-intake form.
- Material desk supports `/resources?course=<course-id>&week=<week-no>`: both parameters are validated against the active course roster, and the week is only a registration default.
- Within course context, queued extraction, pending candidate review, Drive intake, and registered materials are filtered to that course.
- Server resource retrieval itself is limited to the **active semester's active courses**, avoiding leakage of archived-semester sources into the current inbox; when no active courses exist no resource rows are fetched.
- The material desk retains its single authoritative processing/approval write route.

### Independent work before solutions
- A teaching week with released exercises hides corresponding solution links until `exercise_attempt_completed_at` is recorded.
- Exercise-attempt completion requires an explicit checkbox confirming independent work. A click never silently fabricates that confirmation.
- It is a **UI disclosure only**; Google Drive permissions are not altered. Students can still reach a file through Drive and must preserve academic honesty.
- A failed finding submission retains its values, and action response text is displayed with the originating teaching week.

### Real, course-week checkpoints
- New `/practice?mode=weekly-checkpoint&course=<id>&week=<number>` constructs the existing cumulative checkpoint queue from that course's current and earlier skills.
- This is separate from, and does not replace, the semester's scheduled checkpoint rotation. Existing `mode=checkpoint` remains unchanged.
- The completed session contains a deterministic course/week marker in its note. Marking a weekly checkpoint requires an ended matching session **and at least one saved attempt not using solution-exposed independence**.
- If offline events are pending, the milestone is withheld until synchronization. Attempts and session events still use existing idempotent APIs.
- This requirement is checked server-side; the UI alone does not grant progress credit.
- The course week retains the same manual milestone write authority after evidence verification. No schema or database migration is needed.

### Non-goals and remaining work
- Does not add automatic solution grading, source extraction, generative AI, new mastery scoring, or a second planner.
- Completion evidence is based on recorded attempts and a learner's self-grade, **not external authentication of work quality**.
- Remaining P32: real-student, start-to-finish course/semester workflow tests, timetabling simplification, and performance/device QA.
- Verify via unit tests, TypeScript, and Next.js production build; do not call this live-device qualified without checking an actual deployment.
