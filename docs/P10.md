# P10 — Semester Autopilot, Daily Capacity Planning, Recovery Mode, Deadline Pressure & Cross-Course Workload Orchestration

## Purpose

P10 turns StudyOS from a diagnostic system into an operating system for the current day.

The central invariant is:

> Backlog changes priority. It never changes today's capacity.

A missed day therefore cannot create a multi-hour punishment queue on the next day.

## Capacity modes

The default configuration is intentionally editable.

| Mode | Default total | Review ceiling | Focus-item behavior |
| --- | ---: | ---: | --- |
| Normal | 120 min | semester review cap (normally 40) | up to 4 |
| Light | 75 min | 30 min | up to 4 |
| Recovery | 45 min | 20 min | up to 2; heavy optional work deferred |
| Intensive | 180 min | semester review cap | up to 4 |
| Custom | 15–720 min | never above semester review cap | normal focus limit |

A daily mode is an override for that date only. Saving planning defaults does not accidentally promote today's Recovery/Custom choice into the long-term default.

## Planner inputs

The deterministic candidate pool contains:

1. the actual P1/P8 retention queue, already capped by today's effective review budget;
2. actionable P5 weekly workflow steps;
3. explicit deadlines/assignments/administrative commitments;
4. the rotating P8 cumulative checkpoint when due;
5. P9 exam-strategy actions during transition/exam mode;
6. P8 course risk as a priority modifier.

Future teaching weeks and passive states such as `await_material` are never scheduled as work.

## Priority behavior

Deadline pressure is monotonic:

- overdue: maximum deadline pressure;
- within 24h: urgent;
- within 48h: urgent;
- within 3 days: strong pressure;
- within 7 days: moderate pressure;
- within 14 days: mild pressure.

Urgent commitments receive an additional scheduler boost.

After an item from a course is selected, later items from the same course receive a temporary selection penalty. This does not change their underlying risk score; it prevents one course from consuming the whole day when similarly important work exists elsewhere.

## Partial blocks

Some work is splittable:

- material processing;
- exercise work;
- solution reconciliation;
- error repair;
- assignments/deadlines;
- exam weakness repair.

If one of these is the highest-value remaining task but no longer fits in full, StudyOS may allocate the remaining usable block and mark it as partial.

Full timed exams and cumulative checkpoints are not split.

## Recovery Mode

Recovery Mode exists for sickness, disrupted weeks, low-capacity days, or returning after absence.

It:

- lowers total capacity;
- lowers the real review queue, not just the label;
- caps focus items;
- suppresses heavy optional checkpoints/timed papers;
- still permits genuinely urgent deadlines;
- never rolls unused backlog minutes into tomorrow.

This preserves continuity without creating a backlog spiral.

## Commitments

`study_commitments` stores explicit external obligations not reliably inferable from course PDFs:

- assignment;
- deadline;
- exam;
- administrative;
- other.

Each commitment may include a course, due timestamp, time estimate, 1–5 priority, source URL, and note.

Completion is explicit and timestamped.

## Today page

Today now answers, in order:

1. How much capacity do I have?
2. What exactly should I do, in what order?
3. What was deferred because it does not fit?
4. Is a checkpoint/risk/exam transition relevant?
5. What deadlines are open?
6. What is the actual retention queue?
7. How are the courses progressing?

The deferred list is explanatory, not punitive.

## Verified contract

A rollback integration test verified:

```text
authenticated user
→ initialize WS26/27
→ switch today to Recovery
→ total capacity = 45
→ real review ceiling = 20
→ max focus items = 2
→ create urgent 60-minute DGL assignment at priority 5
→ commitment starts open
→ mark complete
→ completion timestamp recorded
→ synthetic transaction rolled back
```

Pure planner tests additionally verify:

- hard capacity is never exceeded;
- Recovery Mode suppresses heavy optional work;
- urgent deadlines outrank somewhat higher ordinary priorities;
- cross-course balancing prevents monopolization;
- twenty-item backlog still leaves the configured budget unchanged;
- deadline pressure increases toward due time.
