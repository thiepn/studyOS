## Critical release blockers fixed in code

### 1. False offline success on HTML login redirects
Previously, the middleware redirected unauthenticated `/api/study/*` writes to the login page. A browser automatically following that redirect could return `200 text/html`; pending replay accepted `response.ok` and deleted the locally queued attempt **without server confirmation**.

- API routes now give `401 application/json` with no-store and an explicit `ok:false` authentication error.
- Online submissions and replay require an actual JSON `ok:true` acknowledgment before claiming the write is saved and before deleting the local queue item.
- 401/403 and permanent validation 4xx errors do not produce falsely confirmed study evidence. Transient responses and genuine network failures can be queued.
- The same confirmation rules apply to session starts and finishes.

### 2. Cross-account offline queue replay
An old pending attempt/session was globally stored by origin; switching THIEPN Accounts on a shared browser could replay one person's attempt to another user's backend session.

- New offline records are tagged with the original browser-session user ID (used solely as a **storage namespace**, never as server authorization).
- Automatic replay and pending counts are limited to the currently signed-in account, and each request is still authorized server-side.
- Existing legacy pending entries *without an owner tag* are deliberately not replayed automatically. They remain in original browser storage for manual inspection/recovery; no attempt is silently deleted or reassigned.
- No cross-device persistence or guaranteed recovery under browser quota/eviction is claimed.

### 3. Stale public health version
`/api/health` previously reported `0.25.0` despite subsequent package releases. It now derives the version from `package.json` and supplies an explicit no-store liveness response. **Liveness does not imply backend/API readiness.**

### 4. Missing initial semester and incorrect origin certification
- An authenticated visit to `/setup` without an active semester is routed to first-semester creation or rollover, instead of throwing during activation loading.
- Production and preview origin checks now require a clean external HTTPS URL. Development alone may use loopback HTTP. Production's missing `APP_ORIGIN` must not silently qualify as local HTTPS.

## Automated built-server acceptance

The GitHub Actions `qualify` job now runs `scripts/acceptance-smoke.mjs` after `npm run build`, starting a **production-mode** Next.js server with existing CI placeholders. It checks:

- `GET /api/health`: 200 JSON, exact package version and no-store.
- `GET /login`: public 200 StudyOS page.
- Anonymous `GET /courses`, `/setup`, `/practice?mode=week&week=1`: login redirect preserving the exact destination.
- Anonymous `POST /api/study/attempt`, `/api/study/session/start`, `/api/study/session/finish` and week milestone: **401 JSON**, no-store, never an HTML login response.
- Unit tests cover malformed/HTML 2xx responses, 4xx/5xx, valid confirmations, cross-user pending replay and invalid production origins.

The smoke uses no production secrets, makes no real write requests to an authenticated backend and does not establish a live browser/device acceptance.

## Additional production security advisory (read-only)

Supabase Security Advisor returned four **StudyOS-scoped** notices:

- Three `authenticated_security_definer_function_executable` warnings on `study_add_reconciliation_finding`, `study_mark_week_milestone`, and `study_resolve_reconciliation_finding`. Their definitions have a pinned `search_path` and include `auth.uid()` and `user_id` logic. Those observations **do not certify** ownership, parameter validation, or all execution paths. Follow the [Supabase security-definer advisory](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable) and perform an explicit second-user forbidden-cross-account test before production certification. No privileges or functions were changed during this phase.
- One informational `rls_enabled_no_policy` notice for the isolated `study_drive_credentials` table. It is expected for a table meant to be inaccessible directly by application clients, but confirm server-side access intentionally uses the service role and clients have no direct grant. See [RLS-no-policy advisory](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy).

These findings are not proof of exploitation and should not be reported as resolved solely from a schema/catalog inspection.
