# P12 — Live Semester Activation, Real Course Timetable & Material Onboarding, Baseline Diagnostics and First-Week Operational Certification

## Objective

P12 stops expanding StudyOS infrastructure and turns the existing system into a certifiable semester workflow.

The phase distinguishes three independent layers.

### 1. Platform certification

The application runtime must have:

- Supabase server credentials;
- a secure HTTPS origin;
- Study Drive OAuth configuration;
- Study Calendar OAuth configuration.

This only proves the platform can operate.

### 2. Pre-semester activation

The signed-in user must have:

- the canonical six-course WS26/27 workspace;
- the intended Study Drive account connected;
- root, semester, inbox, and course folder structure provisioned;
- the intended Study Calendar account connected and synced;
- at least one mapped timetable event for each of DGL, Stochastik, TheoInf, and AMP;
- EiP and Mikro baseline diagnostics completed against real mapped prior-course skills.

Until this layer is complete, StudyOS must not call the personal semester “ready”.

### 3. First-week operational certification

Every major course independently needs:

- at least one verified resource explicitly attached to teaching Week 1;
- at least one active skill;
- at least one active review/practice question;
- at least one recorded attempt.

Therefore certification proves a real end-to-end path, not merely data presence:

```text
real Week-1 material
→ Study Drive
→ registered/processed/verified source
→ skill + question
→ closed-book attempt
→ retention/review state
→ P10 daily plan
→ optional P11 calendar placement
```

All four major courses must prove this path.

## Activation Center

`/setup` is now the canonical activation screen.

It shows:

- Platform certification percentage and blockers;
- Pre-semester activation percentage and blockers;
- First-week certification percentage and blockers;
- Study Drive connection/tree state;
- Study Calendar connection/sync state;
- per-course activation matrix;
- retake-baseline links;
- Week-1 proof counts.

Opening the authenticated Activation Center still calls the existing workspace initializer, so the canonical six courses are created automatically if they do not yet exist.

## Retake baselines

Baseline diagnostics are only valid for courses with `course_kind = retake`.

They operate on the real active skills produced from processed prior course material. If a retake has zero skills, the UI instructs the user to import/process old material first rather than fabricating topics.

For each skill the user performs a closed-book check and classifies it:

- **Retained** — independently retrievable/executable;
- **Rusty** — mostly known but slow, uncertain, or incomplete;
- **Weak** — recognizable but not reliably executable;
- **Never mastered** — was never truly learned.

Classification changes scheduling only:

- retained → `next_review_at ≈ now + 21 days`;
- rusty → `≈ now + 3 days`;
- weak / never mastered → due now.

It does **not** add recall, recognition, execution, transfer, or exam evidence and leaves mastery conservative.

Incomplete baselines become P10 daily planning candidates once real skills exist.

A completed baseline automatically becomes effectively in-progress again if later processing introduces unclassified active skills.

## Data model

P12 adds:

- `study_baseline_diagnostics`;
- `study_baseline_results`;
- `study_baseline_summary`;
- `study_activation_course_status`;
- `study_activation_snapshot`;
- `study_baseline_status`;
- `study_baseline_classification`;
- authenticated baseline start/classify/complete RPCs.

The tables use RLS and all baseline RPCs deny anonymous execution.

## Verified rollback integration

A synthetic retake flow was executed inside a rollback boundary:

```text
initialize WS26/27
→ locate EiP retake
→ create one synthetic programming skill
→ review state auto-created by existing trigger
→ create one diagnostic question
→ start baseline
→ classify Retained
→ complete baseline
→ summary = completed / 1 classified / 1 retained
→ mastery_state remains new
→ sum of mastery evidence remains 0
→ next review moves >20 days into future
→ activation course view sees the retake
→ rollback all synthetic data
```

## Live activation state at implementation time

The shared Supabase project had no initialized StudyOS semester records, no course records, no Study Drive or Calendar connection, no resources, and no skill/question state.

That is treated as an honest **personal activation blocker**, not as a platform failure. P12 code can be fully certified before the user signs into the deployed StudyOS and selects the intended Google accounts.
